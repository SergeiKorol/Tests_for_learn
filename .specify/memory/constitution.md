# Offline Quiz App Constitution

## Core Principles

### I. Offline-First (Офлайн-приоритет)

Приложение MUST быть полностью работоспособным без сети после первоначальной
инициализации (установка PWA и кэширование оболочки). Все пользовательские
сценарии — прохождение встроенного теста, просмотр скачанных тестов, сохранение
результатов, настройки — MUST работать офлайн. Сетевые запросы допустимы только
для явных действий пользователя (проверка обновлений, скачивание тестов) и MUST
корректно деградировать при отсутствии соединения без потери локальных данных.

**Обоснование**: офлайн-режим — ключевая ценность продукта; архитектура не
должна создавать скрытых зависимостей от сети.

### II. Client-Only Architecture (Чисто клиентская архитектура)

Вся бизнес-логика MUST выполняться в браузере. Запрещены серверный рендеринг,
собственный бэкенд и передача пользовательских данных на сервер. Контент тестов
распространяется как статические JSON-файлы во внешнем репозитории (GitHub или
совместимый источник). Приложение MUST уметь загружать тесты по HTTP(S) и из
локального файла на устройстве.

**Обоснование**: отсутствие серверной инфраструктуры снижает стоимость
развёртывания, упрощает приватность и соответствует модели «установил — работает
везде».

### III. Local Storage & Privacy (Локальное хранение и приватность)

Все данные — встроенный ознакомительный тест, скачанные тесты, результаты
прохождения, настройки (включая URL репозитория) — MUST храниться локально в
IndexedDB. Приложение MUST NOT отправлять пользовательские данные, статистику или
телеметрию на внешние серверы. Единственные исходящие сетевые запросы — загрузка
статических файлов тестов и обновление оболочки PWA по инициативе пользователя
или стандартным механизмом service worker.

**Обоснование**: приватность и автономность — нефункциональные требования,
которые определяют доверие пользователя к приложению.

### IV. Progressive Web App & Cross-Platform (PWA и кроссплатформенность)

Приложение MUST быть PWA: web app manifest, service worker, возможность
установки на домашний экран / в меню приложений. MUST поддерживаться все
современные браузеры на Android, iOS, Windows, macOS и Linux. UI MUST быть
адаптивным для экранов от 320px до 4K.

**Обоснование**: единая кодовая база для всех платформ без нативных обёрток —
основной способ достичь кроссплатформенности при минимальных затратах.

### V. Simplicity & Minimal Footprint (Простота и минимальный размер)

Установочный пакет MUST содержать только необходимую оболочку приложения и ровно
один встроенный ознакомительный тест. Дополнительные тесты загружаются по
запросу пользователя. Архитектура MUST следовать принципу YAGNI: новая
сложность допустима только при явной необходимости и MUST быть обоснована в
спецификации или плане фичи.

**Обоснование**: быстрая первая загрузка и понятный onboarding снижают порог
входа; лишний код увеличивает время установки и поддержки.

## Нефункциональные требования

| ID | Требование | Критерий приёмки |
|----|------------|------------------|
| NFR-01 | Офлайн-режим | После первого запуска и скачивания тестов весь функционал доступен без интернета |
| NFR-02 | Кроссплатформенность | Установка и работа как PWA на Android, iOS, Windows, macOS, Linux |
| NFR-03 | Локальное хранилище | Все данные в IndexedDB; перезапуск приложения не теряет состояние |
| NFR-04 | Приватность | Отсутствие исходящих запросов с пользовательскими данными |
| NFR-05 | Встроенный тест | При первом запуске доступен ровно один демо-тест без скачивания |
| NFR-06 | Обновление тестов | Пользователь вручную проверяет наличие новых тестов при наличии сети |
| NFR-07 | Статус тестов | В каталоге отображается статус: «не скачан» / «загружен» |
| NFR-08 | Гибкий источник | Настраиваемый URL репозитория и импорт JSON-файла с устройства |
| NFR-09 | Минимальный bundle | В сборку не включаются тесты, кроме одного встроенного |
| NFR-10 | Адаптивный UI | Корректное отображение на viewport от 320px до 4K |

## Технологический стек и архитектурные ограничения

### Технологический стек

| Слой | Технология | Примечание |
|------|------------|------------|
| Приложение | SPA (HTML/CSS/JS/TS) | Фреймворк выбирается в plan.md; MUST поддерживать tree-shaking |
| Сборка | Vite (рекомендуется) | Быстрая dev-сборка, поддержка PWA-плагинов |
| PWA / кэш | Workbox | Service worker; оболочка — precache; JSON тестов — NetworkFirst |
| Локальное хранилище | IndexedDB (через обёртку, напр. idb) | Абстракция доступа к данным обязательна |
| Контент тестов | Статические JSON | Репозиторий GitHub Raw / GitHub Pages / совместимый CDN |
| Стили | CSS (модули или utility-first) | Поддержка тёмной темы как часть демо-теста |
| Документация | Markdown, язык — русский | README, spec, plan, комментарии к публичному API |

### Архитектурные ограничения

1. **Service Worker (Workbox)**:
   - Precache: HTML, CSS, JS, assets оболочки, встроенный демо-тест.
   - Runtime caching для JSON тестов: стратегия **NetworkFirst** с fallback на
     IndexedDB / cache.
   - Обновление SW MUST NOT удалять локально сохранённые тесты и результаты.

2. **Структура репозитория тестов**:
   - В корне: `index.json` — каталог доступных тестов (id, title, version, url).
   - Папка `tests/` — отдельные JSON-файлы тестов (или аналогичная структура).

3. **Схема JSON теста** (контракт, MUST соблюдаться):

   ```json
   {
     "id": "unique-slug",
     "title": "Название теста",
     "description": "Описание (опционально)",
     "version": 1,
     "timeLimit": 0,
     "questions": [
       {
         "id": "q1",
         "text": "Текст вопроса",
         "options": ["Вариант A", "Вариант B"],
         "correctIndex": 0
       }
     ]
   }
   ```

   - `id` — уникальный slug; `timeLimit` — секунды, 0 = без ограничения.
   - Изменение схемы — MINOR/MAJOR версия конституции и миграция данных.

4. **Слои приложения** (Separation of Concerns):
   - **UI** — компоненты экранов; без прямого доступа к IndexedDB.
   - **Services** — загрузка тестов, синхронизация с репозиторием, импорт файла.
   - **Storage** — единственная точка работы с IndexedDB.
   - **SW** — только кэширование и офлайн-fallback; без бизнес-логики.

5. **Встроенный ознакомительный тест**:
   - Включён в bundle / precache.
   - Демонстрирует: навигацию, прохождение вопросов, экран результатов, тёмную
     тему (как минимум один вопрос на эту тему).
   - MUST NOT требовать сети для первого запуска.

## Процесс разработки и качество

- Спецификации фич (`spec.md`), планы (`plan.md`) и задачи (`tasks.md`) MUST
  соответствовать принципам данной конституции.
- Каждая фича MUST иметь проверяемые acceptance criteria, связанные с NFR.
- Unit-тесты — для сервисов и парсинга JSON; e2e — для критических
  пользовательских сценариев (офлайн, скачивание, прохождение теста).
- Изменения схемы JSON или IndexedDB MUST сопровождаться версионированием и
  стратегией миграции.
- Документация проекта MUST вестись на **русском языке**.

## Governance

- Данная конституция имеет приоритет над локальными соглашениями и MUST
  проверяться при ревью спецификаций, планов и pull request'ов.
- **Поправки**: предложение изменения → обоснование → обновление
  `constitution.md` → semver bump → запись в Sync Impact Report.
- **Версионирование конституции**:
  - MAJOR — удаление или переопределение принципов, несовместимые изменения
    контракта данных.
  - MINOR — новый принцип, NFR или существенное расширение раздела.
  - PATCH — уточнения формулировок, опечатки, несемантические правки.
- **Compliance review**: перед merge фичи проверять соответствие Offline-First,
  Client-Only, Privacy и формату JSON тестов.
- Руководство по разработке — в артефактах Spec Kit (`.specify/templates/`,
  `spec.md`, `plan.md`); конституция задаёт неизменяемые границы.
